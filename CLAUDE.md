# Grasp — AI Note-Taking Website for Students

## 1. Overview

Grasp is an AI-powered note-taking website for students. The core differentiators vs. free tools (Notion, OneNote, Google): near-zero-friction onboarding, contextual AI help embedded directly in notes, and personalized quizzes/resources tied to the student's actual material and assessment criteria.

**Positioning: school-focused, not work/meeting-focused.** Most AI note-taking competitors (including notableai.app and notableai.ca) are built around meetings, work calls, and professional dictation, with lecture/study use as a secondary use case at best. Grasp is built specifically around the school experience from the ground up — subjects/timetable structure, assessment criteria, term planners, quizzes tied to coursework — not repurposed meeting-note tooling. This should shape every design decision: language, UI, feature framing, and marketing should all speak to students/school life, not professionals/workplaces.

Platform: **Website** (not a native app) — no app store fees, no OCR SDK needed, deploys on Railway.

**Naming note:** Originally named "Notable," but two existing AI note-taking competitors (notableai.app and notableai.ca) already operate under that name in the same space — renamed to **Grasp** to avoid trademark/brand confusion risk.

## 2. Onboarding

- First-time signup: user uploads a screenshot of their timetable
- No dedicated OCR needed — send the screenshot directly to a vision-capable model (e.g. GPT-4o) and prompt it to extract subjects/schedule as structured JSON
- AI auto-creates a dedicated notes space per subject (OneNote/Notion-style structure), pre-populated and ready to edit — zero manual setup required

## 3. Core Features

### 3.1 Notes
- AI-enhanced notes: cleanup, formatting, expansion
- Record lecture → AI transcribes (Whisper) → auto-generates structured notes
- **Live note-taking:** while a lecture is recording, the student sees the AI notes being drafted in real time (not just at the end). When the student stops, they name the recording and the AI-generated notes (not the audio) are saved into that subject's notes.
- Manual note-taking also fully supported — notes are directly editable
- Ask AI to explain or correct notes if wrong/confusing

### 3.2 Highlight to Explain
- User highlights any line/section directly within their notes (not a separate chatbot tab)
- AI shows a contextual explanation anchored to that highlight, threaded like a margin conversation
- **Follow-up questions:** the highlight explanation is a thread — the student can ask follow-ups, and the AI can edit the note as a result (e.g. if the student catches a hallucination/error, the AI agrees and corrects the note in place)
- Keeps AI help embedded in the notes UX rather than feeling like a bolted-on chat feature

### 3.3 Subject Quiz Mode
- Each subject has its own Quizzes section
- User selects specific notes/topics to be quizzed on
- User can add custom comments/instructions to guide what the AI focuses questions on
- User chooses the question mix: multiple choice, short answer and long answer, any number of each
- Quizzes are generated from the student's own notes, not generic question banks — personalized studying, not generic tutoring (this is the key differentiator vs. apps like Studdy)
- Quizzes are saved per subject and laid out as cards, the same way subjects are on the home page — a student can come back to a past quiz and see what they scored
- Written answers are marked by the AI against the student's notes; a partly-right answer earns half rather than being failed outright
- After submitting, the student can ask why a specific answer was wrong and get an explanation of that mistake. Only offered on answers that weren't fully right, and only generated when asked

### 3.4 Resource Bank
- Each subject has a dedicated Resource Bank section
- Users upload supporting docs: assessment criteria, term planners, rubrics, past papers, syllabus docs, etc.
- AI references these when generating notes, explanations, and quizzes — e.g. weighting quiz questions toward what's actually assessed, or aligning notes to the term planner/marking criteria
- Makes the AI assessment-aware, not just generically helpful

## 5. Tech / Hosting Plan

- **Frontend/backend:** built via Claude Code
- **AI text generation:** ChatGPT API (chosen for cost) — use a cheaper model (e.g. GPT-4o-mini) for routine note formatting/cleanup, reserve stronger models for quiz generation where quality matters more. **As built:** GPT-4o only for the one-off timetable read. Quiz generation, marking and "Explain why I'm wrong" run on **gpt-5-mini**, a reasoning model (2026-09-17): GPT-4o-mini keyed "2x + 3 = 11" as x = 5 and then explained a correct answer of 4 as a mistake. Reasoning models take `reasoning_effort` (medium for generation, low for marking and explanations) and reject `temperature`. The explanation prompt now works the question out first and says plainly when the answer key, not the student, was wrong. Every other route, the Resource Bank read included, runs on GPT-4o-mini. The Resource Bank read moved from GPT-4o to mini on 2026-09-14 so that one read costs under a cent (see §11).
- **Transcription:** Whisper API — $0.006/min (~$0.36/hour), negligible cost at expected scale
- **Vision/subject extraction:** vision-capable model reads timetable screenshot directly, no separate OCR pipeline
- **Database:** Postgres — stores user accounts, subject structures, note text (small text data, cheap). **As built this is Railway Postgres**, a second service in the same Railway project as the app, so hosting stays in one place. It replaced a Neon database (reached over Neon's HTTP driver) when hosting moved off Vercel; nothing was migrated across. See §11 for the schema and the driver.
- **Audio storage:** none — audio is discarded immediately after transcription to save cost and reduce privacy exposure
- **Billing:** Stripe, added 2026-09-18. Hosted Checkout takes the card; a webhook plus the Checkout return route keep `users` in sync with the subscription (`lib/billing.ts`, §11). The one dependency that is the official provider SDK rather than a raw `fetch` — the same reasons `lib/db.ts` uses `pg` over hand-rolled wire code apply to verifying webhook signatures.
- **Hosting:** Railway (moved from Vercel), free–cheap tier at small scale
- **Domain:** ~$10–15/year

## 6. Tiering / Limits

- **No free plan.** Two paid plans, **Pro** and **Max**, and every new account starts on a **free trial of Pro**. Choosing a plan is the last step of onboarding (see §11). This replaced the original free / paid split at the user's request.
- **Billing is real, through Stripe** (2026-09-18, `lib/billing.ts`, §11). A card is taken by a Stripe-hosted Checkout Session before either plan starts — Pro's trial converts to a real weekly charge on its own when it ends, and Max is charged immediately, since there is no trial-less way to start a paid plan. Grasp's own servers never see a card number.
- **One free trial per card, not per account** (2026-09-18, `lib/trialClaims.ts`, the `trial_claims` table). The account-level guard — a Checkout Session only gets `trial_period_days` when the account's own `trial_ends_at` is still null — stops one account starting a second trial; it cannot stop the same person signing up under a new email, which is the abuse that actually costs money, since every trial opens a fresh week of AI allowances. The card is the only thing that stays the same across those signups, so the claim is keyed on the payment provider's card fingerprint, checked once Checkout actually reveals it — a trial started on a card that has already had one, under a different account, is ended immediately and charged in full rather than refused outright, so the sale still goes through.
- **Students are charged in their own currency, and the allowances are not** (2026-09-19, `lib/currency.ts`). Grasp's costs are in US dollars — OpenAI, Whisper and Stripe all bill in them — so **`PLAN_PRICE_USD` stays the single anchor every allowance is derived from**, whatever a student actually pays. `PLAN_PRICE_BY_CURRENCY` holds the presentment prices on top of it: **AUD A$9.99 Pro / A$19.99 Max**, set by hand near the anchor converted at the rate of the day rather than at a live rate, because a Stripe Price is immutable and a moving rate would silently split students onto different amounts for the same plan. Every plan gives every student the same allowances, so there is one budget, in one currency. At A$1 = US$0.65 the AUD prices come to about $6.49 and $13.00, under the anchor by roughly 7% on Pro and 10% on Max — so a falling AUD eats margin rather than service, and the prices are worth re-checking by hand when it moves.
- **As built** (all in `lib/plan.ts`, prices cut 2026-09-19): **Pro US$6.99 / A$9.99 a week** with a 7-day free trial: 10 quizzes, 1h 40m of recording (up to 20 minutes a recording), 10 Resource Bank reads (5 documents per subject), and 18,000 AI tokens. **Max US$14.49 / A$19.99 a week**: 25 quizzes, 5h of recording (up to 30 minutes a recording), 15 reads (10 per subject), 19,000 AI tokens. Recording is a weekly time allowance, not a count (2026-09-17, at the user's request); the plan cards show only the total time. Both plans are choosable now that billing exists (`PLAN_AVAILABLE`, 2026-09-18).
- **The rule: a plan used to the full costs Grasp at most `AI_BUDGET_SHARE` of its price**, which is **0.59** — so a maxed-out plan costs at most about 58% of what it sold for.
  - **It was 0.5 until 2026-09-19**, when the prices were cut (Pro US$7.99 → $6.99, Max US$16.99 → $14.49) at the user's request, explicitly to take less profit rather than to give less product. Because the allowances are *derived* from the price, holding the share at a half would have done the opposite: Pro's tokens would have fallen 16,000 → 11,000 and **Max's 19,000 → 6,000**, fewer than Pro's on a plan costing twice as much, which stops the tier making sense. 0.59 is the lowest share that holds both allowances at or above where they were. The trade was made knowingly: a thinner worst case over a worse product.
  - **The worst case is deliberately pessimistic**, which is what makes 58% comfortable rather than tight — every figure in `lib/costModel.ts` prices output at its cap, and the costs measured against the real prompts (below) sit far under it. `lib/costModel.ts` holds every input and output cap the AI routes enforce and prices each feature's worst case at those caps; `lib/plan.ts` sums quizzes, reads and recordings at their worst and gives **whatever is left to AI tokens**, rounded down to a thousand. So **the token allowance is never set by hand**: change a price or an allowance and it recomputes. `planWorstCase(plan)` returns the breakdown.
  - **Worst cases at the caps:** a quiz $0.072 (generation $0.029 plus two markings at $0.022, since a retake can be marked again); a Resource Bank read $0.0085; a week's recording time $1.49 on Pro and $4.62 on Max (`recordingTimeWorstUsd`, which prices the time at whichever recording length costs most per second). Maxed out, Pro comes to about $2.29 before tokens against a $4.12 budget, Max about $6.53 against $8.55 — so recording takes most of Max's budget, and is why Max is the plan that suffers first when the price moves. Shortening Max recordings, or redrafting live notes less often than every segment, is the lever for more tokens.
  - **Short recordings are the dear ones**, because every recording brings its own drafts and final pass. So a recording takes **at least a minute** off the week (`recordingMinChargeSeconds`), a recording's drafts are capped by the seconds it was charged (`draftCeiling`: one per 20 seconds plus the final pass), its transcript by the same seconds, and a draft's reply by the transcript it read (`liveOutputTokens`: 500 plus twice its tokens). Without those, a stream of one-second recordings cost several times a lecture per minute.
  - **Measured on 2026-09-17** with the app's own prompts at full input: the costliest quiz (10 MCQ + 10 long) $0.0128, marking 20 written answers $0.0075, a final lecture draft over 30 minutes of speech $0.0022. The worst cases sit well above those because output is priced at its cap. **Re-measure before loosening a cap, or when a model or price changes** (gpt-5-mini $0.25/$2.00, gpt-4o-mini $0.15/$0.60 per million tokens, Whisper $0.006 a minute).
  - Bounds assume about 4 characters a token, which holds for English; notes in Chinese or Japanese can tokenise several times denser.
- Pricing must be set so each plan's price comfortably covers worst-case API cost of a heavy user (biggest financial risk area — see flaws below)

## 7. Legal Requirements

- **Terms of Service:** usage rules, AI liability disclaimer (AI-generated content may be inaccurate), account terms
- **Privacy Policy:** required — covers what data is collected (email, notes, uploaded files), retention, and third-party processing (OpenAI API use). Can start from a cheap/free generated template (e.g. Termly, GetTerms) and refine later.
- Add a disclaimer around lecture recording — some institutions require instructor consent to record lectures; this is a user-responsibility disclaimer, not something the app can enforce.

## 9. Potential Flaws / Risks to Design Around

1. **AI API cost vs. subscription pricing** — heavy users (long recordings, frequent quiz generation) could cost more in API fees than they pay. Mitigate with usage caps per tier and careful pricing.
2. **AI accuracy/content moderation** — wrong AI explanations or quiz answers create a trust problem. Build in a "flag this" / feedback mechanism early.
3. **Competing with free tools** — Notion/OneNote/Google are free and familiar. Differentiation (resource bank + personalized, assessment-aware quizzes) needs to be clearly communicated in onboarding/marketing, or users won't see the reason to switch.
4. **Retention/seasonality** — student tools naturally see usage spikes near exams and drop-off during holidays. Worth considering what brings users back day-to-day beyond exam crunch periods.
5. **Timetable extraction reliability** — screenshots vary wildly in format (school portals, apps, different layouts). Poor extraction accuracy at first use is high-risk since it's the very first thing a new user does — a bad first impression here loses users immediately.

## 10. MVP Scope (build this first)

- Auth + account creation
- Timetable screenshot upload → AI subject extraction → auto-created subject notes spaces
- Manual note creation/editing per subject
- AI note enhancement (cleanup/expand)
- Lecture recording → transcription → auto-generated notes
- Highlight-to-explain within notes
- Quiz section per subject (topic/note selection + question mix + custom instructions + generation, marking, saved results)
- Resource bank per subject (file upload + AI reference during generation)
- Free/paid tier usage limits enforced
- Basic Terms of Service + Privacy Policy pages

No native app, no OCR SDK, no persistent audio storage. Functional over polished — this is a test of concept, not a finished product.

**Status: still being built. Grasp has not launched and has no users.** Every account in the database is one of the developer's own test accounts, every Stripe key is a test-mode key, and no real card has ever been charged. Nothing described below is a live system to be protected.

This changes what a good change looks like, so read the rest of this section in that light:

- **Prefer the clean change to the careful one.** A schema change that drops a column outright, resets every account, or changes how plans are stored costs nothing but re-running `npm run db:setup` and signing up again. Don't write a backwards-compatible migration, a dual-read fallback or a default-then-drop dance to protect data that is all disposable — unless the goal is to have that machinery in place *before* launch, which is a different reason and worth saying out loud.
- **Where an entry says "production", read "the Railway deployment"** — an environment the developer tests against, not a live product with students on it.
- **Where an entry says a default was added "so nobody was locked out" or "so nobody was sent back through onboarding", that means the developer's own test accounts.** It is a record of what was done, not evidence that user data needs protecting.
- **Don't gate work on "this would disrupt users" or soften a feature because it isn't live yet.** There are no users to disrupt. Conversely, don't ship something half-finished on the grounds that nobody will see it — the point of the work is to be ready to launch.

Three` reads the way it does in Word and Docs instead of restarting at 1. Any item margin made lists read looser than the prose around them. - **The placeholder is a measured element, not CSS, and it is always the plain base text** (2026-09-21, at the user's request). As a `::before` pinned to the editor's top-left it sat on top of a bullet or checkbox whenever the first block was a list item, so `NotesTab` measures where the first character will land and renders a positioned span there — beside the bullet, the number or the checkbox. - **The editor's content sync compares without caret marks** (`stripCaretMark(el.innerHTML) !== html`). A live mark is never in the stored body, so a plain comparison read it as a change and rewrote `innerHTML` straight after a toolbar press, which dropped the caret onto the editor element itself. From there `blocksInRange` found no block and the next list button silently did nothing — pressing Bullet points then Numbered list on an empty note left it bulleted. `blocksInRange` now also resolves a caret sitting on the editor element by position, as a second line of defence.
- **`DEFAULT_TEXT_COLOR` is `#4a453f`, the editor's own `text-slate-700`** under the warm neutral scale. It was Tailwind's stock `#334155`, which untouched text never matched, so every toolbar press on an empty line planted a `<font color>` nobody had picked. If the editor's text colour changes, change this with it.
- **The armed caret is styled by an invisible marker, which must never be persisted.** Formatting armed on a collapsed caret (bold with nothing selected) changes no markup, so the blinking caret itself stays whatever size it already was. `NotesTab` plants a `CARET_MARK` (U+FEFF) wrapped in the armed `<b>`/`<i>`/`<u>`/`<font>` so the caret renders at the armed formatting immediately, and removes it once a real character lands. Two rules keep it from leaking: `removeCaretMark` reads the text node's `parentElement` **before** detaching it — read after, it is always `null`, which left the empty `<b>` behind on every single arming — and `commit` runs the saved HTML through `stripCaretMark`, because a toolbar press commits *before* it re-arms and a structural key (Enter, Backspace in a list) commits without going near the mark at all. A leaked mark is invisible but corrosive: `isEmptyHtml` reads U+FEFF as whitespace, so the note still looks blank while carrying a `<b></b>` the student can neither see nor delete. `caretOffset` correspondingly does not count marks, so the offsets it records match the stripped HTML they are restored into.
- **`blockTextStart` (in `lib/richText.ts`) must not collapse its range.** It reports where a block's text begins, and is shared by the placeholder and the checklist box's hit area (the box is a pseudo-element with no rect, so it is defined as the 26px before the text). That fallback happens to be correct for left-aligned text, so the bug stayed invisible until blocks could be centred, at which point centred and right-aligned checkboxes stopped responding to clicks. Before this, un-checking the *second* of two checklist items left an 8px smaller gap than un-checking the *first* did — the same action moving the text by different amounts depending on where it sat. Keep any new block type inside this rhythm.
- **Note storage format**: bodies are HTML (`lib/richText.ts`), and `updated` is an ISO timestamp. It used to hold the *label* — the seed set it to "2 hours ago" and the note list printed it verbatim, so a stored note kept claiming an age it had long outgrown, and once it round-tripped through a real `timestamptz` column the student was shown a raw `2026-08-31T09:02:05.470Z`. `updatedLabel` in `lib/schedule.ts` derives the wording at render time instead, off the client-only `useNow()` clock so it neither drifts on hydration nor goes stale while the tab is open. **A save keeps each note's own `updated` time** (2026-09-21, `noteStamp` in `lib/subjectsDb.ts`). Every save rewrites every note in the subject, and the insert used to stamp `now()`, so editing one note reset "3 days ago" to "just now" on all of them. Checklist state travels to the AI as `[x]` / `[ ]`, bullets as `- `/`1. `, equations as their `data-tex` source.

It explicitly must **not** add a "Key takeaways" or "Summary" section; earlier versions did and that read as bolted-on rather than as the note being better. - **Sanitiser** (`sanitizeNoteHtml`): everything entering the editor from outside — the enhance response, the explain/refine response, clipboard paste — is stripped to an allowlist of tags/attributes via an inert `DOMParser` document. Audio is never stored (§5): it goes straight through the route to the provider and the buffer is dropped when the request ends — nothing is written to disk and no blob is persisted.
- **The recorder restarts itself on an interval rather than streaming** (`lib/recorder.ts`). `MediaRecorder` produces a *stream*, not a series of files: only the first chunk carries the container header, so chunk N on its own will not decode and Whisper rejects it. Re-sending the whole recording each time would make cost grow with the square of the lecture, and hand-reassembling headers is fragile and differs per container — so the recorder is stopped and restarted every 20s, which makes each segment a complete valid file. The `MediaStream` stays open across restarts, so the student is only asked for the microphone once.
- **Two things are dropped before they are ever sent.** A segment shorter than 1s: Whisper rejects anything under 0.1s outright (`audio_too_short`), and `stop()` flushes the segment in progress, so stopping shortly after a boundary used to throw a transcription error at the exact moment the student finished — only that trailing flush can ever be short, and a sub-second tail is the sound of someone reaching for the button. And a segment whose peak level never crosses `SILENCE_PEAK`: Whisper *hallucinates* on silence (two seconds of digital silence comes back as "you"), so a quiet spell would inject words the lecturer never said into the notes and pay per request to do it. The level is read from an `AnalyserNode` tapped off the same stream, so nothing has to be decoded back out; if metering is unavailable it sends everything rather than risk dropping speech.
- **Segments are transcribed through a promise chain, never in parallel** — two requests in flight can resolve out of order and stitch the lecture together backwards. Drafts run inside the same chain, so `stop()` drains it and then makes one final pass over the complete transcript.

Deterministic, so it cannot relapse. Runs after the sanitiser, since folding only ever produces already-allowed tags.

Measured in-browser, not assumed: pressing Back inside the app fires `popstate`, changes the URL, and **keeps the same document** — it is a client-side route change, so `beforeunload` never fires and the provider unmounts silently. - **Accounts and Postgres (§10) — real, and the localStorage era is over.** Signup, login, logout and a session cookie, with every subject, note, quiz and resource stored in Railway Postgres and scoped to a user. The only thing still in `localStorage` anywhere is `grasp.hideNoteTip`, which is a per-device UI preference and belongs there.
  - **`db/schema.sql` is the schema, `npm run db:setup` applies it.** There is no `psql` on a stock Windows box, so `db/setup.mjs` reads `DATABASE_URL` out of `.env.local` by hand (nothing loads dotenv for a bare node process), splits the file on `;` and runs the statements one by one so a failure names the one that broke. It refuses a `*.railway.internal` URL outright, since that address only resolves inside Railway; from a laptop it needs the Postgres service's `DATABASE_PUBLIC_URL`. Every statement is `if not exists`, so re-running is harmless. It is a setup script, not a migration system: the day the schema has to *change* shape rather than grow, this needs replacing.
  - **`pg` is the only npm dependency besides next/react**, used through one pooled client in `lib/db.ts`. It replaced `@neondatabase/serverless`, whose HTTP transport only Neon answers, when the database moved to Railway. Railway runs the app as one long-lived Node server, so a pool has somewhere to live. The pool sits on `globalThis` so dev hot reloads reuse it rather than leaking connections, and it has an `error` listener, because an idle connection the server drops otherwise crashes the process. `sql` is still a tagged template returning rows, rebuilt as `$1, $2, ...` bound parameters, so no query code changed. Any Postgres works, a local one included. Next already treats `pg` as a server external package, so no config was needed.
  - **`query()` in `lib/db.ts` distinguishes "no tables" from "no database", and that distinction was learned the hard way.** A reached-but-empty database returned "Grasp could not reach its database", which sent a real debugging session hunting through connection strings and hosting environment variables when the actual cause was `npm run db:setup` having been run against a *different* database than the one the deployment used. Postgres reports `42P01` (`undefined_table`) for this, which the driver does surface; the message is matched as a fallback. It now says "Grasp's database has not been set up yet" and the server log names the fix. **If you add a database failure mode, give it its own wording** — a message that describes the wrong failure costs more than a vague one.
  - **`lib/db.ts` builds its client on first use, not at module load.** `neon()` throws immediately on a missing connection string, and these modules are imported while Next collects page data at build time, so constructing it eagerly failed the whole build on any machine without a `DATABASE_URL`. Every database call goes through `query()`, which returns a typed failure rather than throwing, and logs the driver's own error server-side only — several of its failure modes quote the connection string, password included.
  - **Passwords are scrypt via `node:crypto`** (`lib/password.ts`), stored self-describing as `scrypt$N$r$p$salt$hash` so the cost parameters travel with the hash and can be raised later without invalidating anyone's password.
  - **The session cookie holds 32 random bytes; the database stores their SHA-256** (`lib/session.ts`). A dumped `sessions` table therefore hands out no usable sessions. Log out deletes the row, not just the cookie — a cookie the browser merely forgets is still a valid credential anywhere it was copied.
  - **`proxy.ts` (Next 16's `middleware`) is not the security boundary and says so.** It checks only whether a cookie is *present*, never whether it is valid, because it runs on every request including prefetches. It exists to keep signed-out visitors off the app shell and signed-in ones off the login page. `requireUser()` is the real check and every data route opens with it.
  - **`/signup` is deliberately *not* redirected for a signed-in device**, unlike `/login`. It used to be, which made the landing page's Sign up button drop anyone with a session straight into the old account — someone on a shared or family device could not make their own. The form used to say "You are logged in as ... Creating a new account will log you out of it"; that notice was removed at the user's request, so the form looks the same signed in or not. The signup route still calls `destroySession()` before `createSession()` so the previous account's session row is ended rather than left valid (verified: the old cookie reads back as signed out). This was never an anti-multiple-accounts measure; a private window always got around it.
  - **Every query in `lib/subjectsDb.ts` is scoped by `user_id`, including lookups by primary key.** Subject ids are minted client-side and so are guessable; `where id = $1` alone would let any signed-in student read or overwrite another's notebook. Verified by trying it from a second account: the write is refused and the victim's data is untouched.
  - **`npm run check:scoping` fails the build on a query that forgot that scope** (`scripts/check-scoping.mjs`, 2026-09-19). The scope above is the whole authorisation model, and it is enforced only by whoever writes the query remembering to add it — so the one mistake that matters is an omission, and an omission is what a text scan can actually catch. It reads every `sql` template under `lib/` and `app/`, works out which tables each touches, and requires `user_id` (or, for the tables hanging off a subject, `subject_id`; or a single-use `token_hash`/`fingerprint_hash` for the auth tables) **in the statement's predicate**, not merely somewhere in it.
    - **Checking the predicate rather than the whole statement is the entire point, and the first version got it wrong.** `select user_id from subjects` names the column while returning every student's subjects, and the first draft passed it — which would have made the scan worthless in precisely the case it exists for. `predicateOf()` therefore takes only what follows `where`, plus join conditions; an `insert` is the exception, where `user_id` in the column list is what binds the row to its owner.
    - **Verified by probe, not by it passing.** A check that has never gone red is indistinguishable from one that cannot. A throwaway file of deliberately unscoped queries was scanned and each rule confirmed to fire, including the three select-list false negatives above, then deleted.
    - It also refuses an `update` or `delete` with no `where` at all, and `users` not narrowed to one account. `auth_attempts` is exempt (`db/schema.sql` says why: most rows are attempts against addresses with no account). An acknowledged exception is written **into the SQL** as `-- scope-ok: <reason>`, so it is reviewed rather than silent.
    - **It cannot prove a query is safe**, only that the scoping column restricts it — a text scan is not a SQL parser, and the child tables' safety still depends on statement order in `saveSubject`. It is a tripwire for the omission, nothing more, and the comment at the top of the script says so.
  - **Postgres row level security was considered and declined (2026-09-19). Don't add it without raising it first.** Three things make it a poor fit rather than a missing best practice: Railway connects as the table *owner*, and **owners bypass RLS silently**, so policies would appear to be in force while doing nothing; `lib/db.ts` is one shared pool with no per-request user identity, and the obvious `set_config` is session-scoped, so on a pooled connection one request's user id leaks into the next — a cross-account leak inside the machinery meant to prevent one; and it could not cover the auth tables anyway, since `lookupSession()` reads `sessions` by token hash *before* it knows the user, `auth_attempts` has no `user_id`, `trial_claims.user_id` is deliberately nullable, and the Stripe webhook looks a user up with no session at all. The scan above catches the same mistake a policy would, one step earlier, and cannot take the site down. If it is ever revisited, `force row level security` plus an `AsyncLocalStorage` request context is the shape, and it needs a non-owner role in Railway.
  - **`saveSubject` returns `false` when the id belongs to someone else rather than throwing.** A throw reaches `query()`, which cannot tell a refused write from a dropped connection — so a rejected overwrite came back as a 502 "Grasp could not reach its database" and was logged as a database fault. The route turns the `false` into a **404** rather than a 403, since a 403 would confirm the id exists (the same reason the login route refuses to say whether an email is registered).
  - **Writes are debounced per subject** (`FLUSH_MS` in `subjectsStore`), which is not an optimisation: `updateSubject` runs on every keystroke in the note editor, and against Postgres-over-HTTP that is a request per character. A `visibilitychange` handler flushes anything still pending with `keepalive`, so closing the tab mid-sentence does not lose it.
  - **`isoDate` in `subjectsDb` reads a `date` with local getters, never `toISOString()`.** The driver parses a bare `2026-11-12` into *local* midnight, so round-tripping it through UTC moved the day for anyone east of Greenwich — caught in testing as an exam saved on the 12th reading back as the 11th, with every countdown built on it a day out. An exam is a day, not an instant, so there is no timezone question here, only a formatting one.
  - **Signup offers the name field (optional), so onboarding does not ask.** `/onboarding` is the three questions and the plan, and it sits behind the proxy like the rest of the app — the account exists before a student ever reaches it.
  - **Signup asks for the password twice**, and a mismatch is refused in the form before anything is sent. Only the form checks it: the route is sent one password, and a mistyped one is the mistake the second box exists to catch.
- **Forgot password** (2026-09-17). A "Forgot password?" link beside the login form's Password label goes to `/forgot-password` (email in, `POST /api/auth/forgot`), which mails a link to `/reset-password?token=...` (new password twice, `POST /api/auth/reset`). Logic in `lib/passwordReset.ts`, screens in `components/auth/PasswordReset.tsx`, which reuses `AuthForm`'s exported `Field` (it gained an `aside` slot for the link). Verified end to end by the user against their own Resend account.
  - **The forgot route answers the same whether or not the address has an account, and does not wait on the send**, so neither the wording nor the response time says who is registered. The screen reads "If {email} has a Grasp account, a link ... is on its way".
  - **Links are a sha256 in `password_resets`** (like sessions and confirmation links), last 60 minutes, and are sent at most once a minute per account (`RESEND_COOLDOWN_SECONDS`); a mail that fails to send deletes its row. Rate limited by a `reset` scope in `lib/rateLimit.ts` (5 per account / 30 per address per hour) that counts **every** request, since each can send an email.
  - **Opening the link spends nothing** (the page only checks it, so a mail scanner visiting first is harmless); setting the password does. It clears every reset link and **every session** the account has, confirms an unconfirmed email (the link proves the inbox), and sends the student to `/login?reset=1` rather than signing them in. A dead link shows "This link cannot be used" with a button to send a new one.
  - The Privacy Policy lists reset link records and Resend sending them. `password_resets` was applied with `npm run db:setup`.
- **A session ends after 30 minutes away from Grasp** (2026-09-17). `sessions.last_seen_at` (grown with `alter table ... add column if not exists`, applied with `npm run db:setup`) is refreshed by any session lookup, at most once a minute; a lookup that finds it older than 30 minutes deletes the row. "Away" means no open tab: `SessionHeartbeat` (mounted in `AppProviders`) pings `POST /api/auth/heartbeat` every 5 minutes and whenever the tab becomes visible, so a student who stays on the site is never signed out, and a 401 from it sends them to log in. `guardAppPage`, `guardOnboardingPage` and `/verify-email` send a stale session to `GET /api/auth/expired`, which clears the cookie and redirects to `/login` — a server page cannot delete a cookie, and while it exists `proxy.ts` would bounce `/login` back to `/home`. A database failure is still left alone rather than signing anyone out. Verified against the dev server: 25 minutes idle stays signed in and is refreshed, 31 minutes goes `/home` → `/api/auth/expired` → `/login` with the row gone.
- **The Resource Bank's empty state is generic** (2026-09-17): "Add anything that helps", naming handouts, worksheets, past papers and textbook pages rather than leading with assessment criteria, since a resource can be anything.
- **The account routes are rate limited (`lib/rateLimit.ts`, `auth_attempts` table, 2026-09-16).** Without it `/api/auth/login` answered a guess as fast as the network allowed, and since scrypt is ~100ms of CPU by design, an unbounded guessing run was a denial-of-service against the server at the same time as a password attack.
  - **Two buckets per attempt, defending different things.** The **account** bucket (the email tried, or the user id for a password change) is the real defence: an attacker working a wordlist against one student cannot avoid it, because hitting that account *is* the attack. The **address** bucket (the caller's IP) is secondary and deliberately loose — schools NAT a whole site behind one address, so a class logging in together must not lock each other out, and `X-Forwarded-For` is spoofable by anyone upstream of the proxy anyway. Thresholds in `RULES`: login 10 per account / 100 per address per 15 minutes, signup 5 / 40 per hour, password change 10 / 100 per 15 minutes.
  - **Signup counts successes, not failures** — the abuse there is creation that *works*. Each account sends a Resend email and opens a trial with its own weekly AI allowance, so bulk creation spends real money; the taken-email 409 is counted too, since hammering it is how a stranger enumerates who has an account. Login and password change count failures only.
  - **A successful login clears its account bucket**, so the tries it took to remember a password do not count against the next login. The address bucket is deliberately *not* cleared: one correct login among many wrong ones is exactly what a successful guessing run looks like.
  - **Buckets are stored as a sha256**, like session tokens and confirmation links. Counting is equality and nothing else, so the table holds no email address and no IP in the clear. `auth_attempts` is correspondingly **not** tied to `users` (most rows are attempts against addresses that have no account, so there is nothing to reference) and is pruned by age — a 24-hour sweep that runs on ~2% of writes rather than on a schedule there is no scheduler for.
  - **It fails open when the database is unreachable.** The route behind it needs the same database and is about to fail with a message that names the real problem; refusing here would report a lockout that is not happening. A database fault is likewise never recorded as a failed attempt, or a blip would lock students out of accounts they typed correctly.
  - **One message for every refusal** ("Too many attempts. Please wait a few minutes and try again."), so it confirms nothing about whether the address exists — the same discipline as the login route's single rejection message.
  - Verified against the dev server: the 11th login attempt returns 429; a *different* email from the same IP still gets a normal 401; and after a correct password, eight prior failures are forgotten.
- **`/admin` switches a browser between Pro, Max and unlimited mode** (2026-09-17, for working on pricing and enforcement). A password screen, then the two `PlanCard`s with a switch on each, "The account's own plan", and an Unlimited mode toggle.
  - **The password is `ADMIN_PASSWORD`, never a constant in the source**, since the repo is on GitHub. Unset, nothing unlocks. Unlock attempts are rate limited (`admin` scope in `lib/rateLimit.ts`: 10 per address, 30 in total, per 15 minutes).
  - **State is a signed session cookie, not the database** (`lib/admin.ts`, `grasp_admin`): no `expires`, so it ends when the browser closes, and the account's stored plan is never written. The HMAC key is derived from the password, so a hand-edited cookie is refused and changing the password voids every unlocked browser. Unlocking needs no Grasp login; the settings apply to whichever account is signed in on that browser.
  - **Applied once, in `lookupSession()`**, so every limit check and `/api/auth/me` follow it without knowing about it. A forced plan also clears `trialEndsAt`, so it reads "Max" rather than "Max trial". It only applies to an account that already has a plan, so it never skips onboarding.
  - **Unlimited mode** adds `unlimited` to the session user and the profile. `lib/usage.ts` claims nothing (so none of it counts towards the account's real week once switched off), `allowance` returns `limit: null`, the per-subject Resource Bank cap is skipped server-side and in the tab, and recordings have no length cap. The per-read document size caps in `lib/resourceLimits.ts` still apply. The header chip, dashboard allowance tile, Record tab, quiz setup, Resource Bank and Settings all say "Unlimited".
  - An already-open Grasp tab only picks a change up on refresh, since the profile is read once on mount.
- **Password strength is a blocklist, not composition rules** (`passwordProblem` in `lib/accounts.ts`). The length floor alone let through `password123`, `12345678`, `iloveyou` and `qwerty123` — all over eight characters and all guessed in the first few hundred attempts of any real attack. `COMMON_PASSWORDS` blocks a few hundred of the most reused ones (plus the ones this product invites: `grasp`, `student123`, `school123`), and a password that is one character repeated, a single sequential run (`abcdefgh`, `87654321`), or contains the account's own email local part is refused too. Still **no** "one capital, one symbol" rule: that pushes people to `Password1!`, which is on every wordlist, and NIST dropped the advice years ago — length plus not-already-everyone's-password is what costs an attacker. `passwordProblem` takes an optional `email` so the form catches the address case without a round trip; `AuthForm` and Settings both pass it.
- **The Resource Bank's per-subject document cap is enforced server-side now**, not only by the tab disabling its Add button. A disabled button is a courtesy to the student; anything that can post JSON ignores it, and `/api/resource-extract` is the route that spends money. `bankIsFull` in that route counts the subject's `resources` rows **scoped by `user_id`** (subject ids are minted client-side and so are guessable — the same reason every query in `lib/subjectsDb.ts` carries the user) and returns a 429. A subject the database has not seen yet is allowed through rather than refused: subjects are written by a 900ms debounced save, so a document added within a second of creating the subject has no row to count, and refusing a legitimate first upload is worse than letting one past a cap the weekly read allowance already bounds. `extractResource` in `lib/ai.ts` gained a `subjectId` for this.
- **Email confirmation on signup — an unconfirmed account cannot use the app.** Signup signs the student in, sends a link through Resend and lands them on `/verify-email` ("Check your email", a resend button, and Log out for a mistyped address). The link hits `GET /api/auth/verify`, which confirms the account and goes on to `/onboarding`, or `/home` if the account has already chosen a plan. Verified end to end against the dev server with a throwaway account.
  - **Enforced twice, for different reasons.** `requireUser()` refuses an unconfirmed account with a 403 and `unverified: true` on every data and AI route; only `/api/auth/verify/resend` opts out, with `allowUnverified`. `guardAppPage()` runs in the `(app)` layout and `guardOnboardingPage()` in `app/onboarding/layout.tsx`, so the student is redirected before the shell renders rather than seeing an app whose every request is refused.
  - **`users.email_verified_at` was added with `default now()` and the default dropped straight after** (`db/schema.sql`). That confirms every account that existed before this shipped -- the developer's own test accounts -- so none of them was locked out, while new accounts start `null`. Both statements are safe to re-run.
  - **`users.plan` and `users.trial_ends_at` were grown the same way** (2026-09-12): the defaults put every account that already existed (all test accounts) on Pro with a 7-day trial from that day, so none was sent back through onboarding, and were dropped so new accounts start `null`. `users.onboarding` (JSONB) holds the answers. Applied with `npm run db:setup` against the Railway database; **the app reads these columns on every session lookup, so a database without them signs everyone out.**
  - **Links are stored as a sha256, like sessions** (`email_verifications`), last 24 hours, and earlier links stay valid when a new one is sent. All of an account's links are cleared once one works. **A second click on a used link is not an error:** the route checks whether the signed-in student is already confirmed, because mail scanners open links before people do.
  - **Resend is one email a minute per account** (`RESEND_COOLDOWN_SECONDS` in `lib/verification.ts`), counted off the newest link's `created_at`. A mail that fails to send deletes its row, so a failure does not start the cooldown. A failed send does not fail signup either; the account exists and the page can send again. It is not silent, though: signup answers `emailSent: false`, `AuthForm` then goes to `/verify-email?status=unsent`, and that page says the email could not be sent and to send it again. It used to show "Check your email" for a mail that never left.
  - **`lib/email.ts` is a raw `fetch` to Resend, not the SDK**, the same discipline as `lib/openai.ts`: the provider's reply is logged server-side and never returned.
  - **Two env vars will matter at launch.** Without `EMAIL_FROM`, mail goes from `onboarding@resend.dev`, which Resend only delivers to the address the Resend account was made with — fine now, useless once there are real students, so a verified sending domain is a launch requirement. `APP_URL` pins the address the link points at, since behind a proxy the request's own origin is not guaranteed to be the public one.

**Design conventions:**

- **Absolutely no emojis. Anywhere. Ever.** Not in UI copy, not in placeholder or seed data, not in AI-generated output shown to the user, not in code comments, not in commit messages, not in chat replies about this project. Emojis make the product read as AI-generated and cheapen it. This rule has no exceptions — if something needs a glyph, it gets an inline SVG icon.
- All icons live in `components/icons.tsx` as inline SVG (Lucide-style, 1.75 stroke). Add to that file rather than reaching for a character.
- No decorative Unicode substitutes for emojis either — no `✓`, `✗`, `→`, `⚠️`, `★`. Use an SVG icon, or plain words.
- Subjects are represented by a monogram (first letter) on a coloured gradient tile.
- Subject colours come from `lib/subjectColors.ts` and are auto-assigned on creation, then editable per subject.

**Visual identity (rebuilt this session).** The palette, the type and the mark are all defined once and inherited; almost nothing sets a colour of its own.

- **`brand` is orange, taken from the logo** (`brand-500` #f26134, `brand-600` #dc4a20 for anything with white text on it). It is the only saturated colour in the product, so it is spent on **one** thing per screen — the action the student is meant to take — and never on decoration. That is why the notebook cards' "Open notes" is navy: a grid of eight orange buttons is eight things shouting equally, and the orange is kept for the tile that starts something new.
- **`slate` is overridden, not extended** (`tailwind.config.ts`). Tailwind's own slate is a cool blue-grey which fights an orange accent and reads cold beside the navy ink; ours is a warm neutral scale with a trace of the brand hue in it. The names were kept so the hundreds of existing `slate-*` classes carried over unchanged — **read "slate" as "the neutral scale", not as blue-grey.**
- **`ink` (#0b2340) is the navy of the notebook in the mark.** Headings, primary text, the avatar, and the one dark surface (the landing CTA and the auth panel).
- **Two typefaces, loaded through `next/font/google` in `app/layout.tsx`** as `--font-display` / `--font-sans`. Bricolage Grotesque carries headings — `globals.css` applies it to `h1/h2/h3` globally, so a heading does not need a `font-display` class. Plus Jakarta Sans does everything a student actually reads. Both are variable, so extra weights cost nothing.
- **The mark is a spiral-bound notebook with the bookmark cut *out* of the cover** (`LogoMark` in `components/Logo.tsx`) — one path with `fillRule="evenodd"`, so the bookmark is a hole rather than a second shape in a second colour. That keeps it legible at 16px and lets it take `currentColor` anywhere. `LogoTile` is the mark in navy on its orange tile, which is the brand as drawn; **white-on-orange would be a different logo.** `app/icon.svg` is the same artwork as the favicon.
- **Motifs are drawn from the subject, not from a stock texture.** `.ruled` in `globals.css` is notepaper at the editor's own 28px line-height, and the landing hero's highlighter swipe behind "understand school" is the product's signature gesture. There is no dot grid any more.
- The landing page, login/signup (a two-panel layout, navy on the left), and onboarding were rebuilt on top of this; every other screen picked the identity up through the tokens.

**API layer:** `lib/ai.ts` calls server-side routes under `app/api/*` through one shared `postJson` helper — plus `postForm` for `/api/transcribe`, since audio can't be stringified into JSON and `fetch` has to set the multipart boundary itself. There is **no `openai` npm package** in this project; `package.json` is next/react/react-dom plus `pg` for the database, and every provider call is a raw `fetch` inside `lib/openai.ts`. Text routes (`/api/enhance`, `/api/generate`, `/api/explain-chat`, `/api/quiz`, `/api/mark-quiz`, `/api/quiz-explain`, `/api/live-notes`, `/api/resource-extract`, `/api/timetable-extract`) go through `chatCompletion()`; `/api/transcribe` goes through `transcribeAudio()`, which is multipart and so can't share that path but masks failures identically. That helper is the only place a provider failure is logged (`console.error`, full detail, server-side only) — the client always gets back the same generic `"Grasp could not reach the AI just now. Try again in a moment."` string. **Never let a raw OpenAI error object reach `NextResponse.json`** — its `message` field echoes back a masked version of the API key, and a route that returns it verbatim will display that in the browser. The `OPENAI_API_KEY` env var itself is only ever read server-side inside `lib/openai.ts`.

**Local `OPENAI_API_KEY` footgun (Windows):** if AI calls fail with `invalid_api_key` even though `.env.local` has a correct, active key, check for a stale `OPENAI_API_KEY` set as a **Windows user-level environment variable** (`[Environment]::GetEnvironmentVariable("OPENAI_API_KEY","User")` in PowerShell) — Next.js's dotenv loader does not override a var that's already present in `process.env`, so an old OS-level key silently wins over `.env.local` with no warning. If you clear it, note that the fix only takes effect for **brand-new process trees**: an already-running shell (and anything it spawns, including a backgrounded `npm run dev`) keeps the value it inherited at its own launch. `unset OPENAI_API_KEY` and the `npm run dev` restart must happen in the *same* shell invocation, chained together, or the unset silently doesn't reach the server process.

## 12. Workflow

**Always push changes to GitHub after committing.** This repo is the source of truth for deployments. After creating a commit (whether via git or through Claude Code), immediately push to `origin main` with `git push origin main`. If there are uncommitted changes at the start of a session, commit and push them as well.

Rationale: Without pushing, your work is siloed on this machine and doesn't reach Railway, making the deployed site stale. Pushing after every commit keeps deployments in sync.
